Test A — Origin inheritance (zero-infra, live chooser)

Opens a child window in an inherited/opaque-origin context, then triggers the picker/chooser inside it. Watch what origin each dialog header shows vs. the child's real origin/URL reported below. Finding = dialog shows this opener's origin (or blank/null) while the child URL is something else.

Why these
  • about:blank & blob: inherit the opener's origin — does the dialog label say so, or show the funny URL?
  • data: is opaque/blocked top-level — does the dialog show null, blank, or refuse? Any non-refusal is informative.
  • The child has Contacts, Bluetooth, and USB buttons — compare the origin across all three dialogs.

Test C — Navigation race & modal lifecycle

Opens a child; you tap Start to fire the chooser, then the child auto-navigates to the target after a delay. Watch whether the modal dismisses, persists (and what origin it then shows), and whether the promise resolves after navigation.

  • Watch: does the modal dismiss on navigation, persist over the target page, or change its origin?
  • Jackpot: a "RESOLVED after navigation" log = a device approved for the opener delivered into the target context.
  • Cross-origin targets (google.com) can't report back after navigating — use a same-origin target (e.g. this page's URL) to observe post-navigation resolution in the log.

Test D — Side-by-side / split view (desktop)

Opens a trusted site in a second window on the right half of the screen. Then trigger a chooser in this window and observe whether the modal is bound to this window or appears associated with the other. Note: desktop uses a different chooser UI than Android's ItemChooserDialog.
